⬡ Що таке операційна система

Операційна система (ОС) — це шар програмного забезпечення між апаратурою і прикладними програмами. ОС виконує три фундаментальні ролі:

  • Менеджер ресурсів — розподіляє процесорний час, пам'ять, диск, мережеві інтерфейси між конкуруючими процесами.
  • Абстрактна машина — приховує апаратні деталі за зручними API: замість регістрів контролера диска — системний виклик read(); замість портів NIC — сокети.
  • Захисник — ізолює процеси один від одного й від ядра, контролює права доступу до файлів і ресурсів.
⬡ Ядро vs userspace

Сучасний процесор підтримує щонайменше два режими виконання — kernel mode (привілейований) і user mode (обмежений). Усі процеси користувача працюють у user mode і не мають прямого доступу до апаратури. Щоб отримати доступ до ресурсу, процес виконує системний виклик — переходить у kernel mode через спеціальну інструкцію (syscall на x86-64).

Прикладні програми · браузер, IDE, ваш скрипт — user mode
Системні бібліотеки · libc (printf, malloc, fopen) — обгортки навколо syscalls
Інтерфейс системних викликів · open, read, write, fork, exec — межа між user і kernel
Ядро Linux · планувальник, керування пам'яттю, файлові системи, мережевий стек, драйвери
Апаратура · CPU, RAM, диски, NIC, GPU
⬡ Linux: ядро vs дистрибутив

Linux — це лише ядро: набір програм, які керують процесами, взаємодіють з апаратною частиною, надають драйвери й модулі. Повноцінна операційна система на основі цього ядра називається дистрибутивом: ядро плюс командна оболонка, системні утиліти, графічне середовище, менеджер пакетів.

Сім'я Дистрибутиви Менеджер пакетів
Debian-based Debian, Ubuntu, Linux Mint apt / apt-get (.deb)
Red Hat-based RHEL, Fedora, CentOS dnf / yum (.rpm)
Arch-based Arch, Manjaro pacman
SUSE-based openSUSE, SLES zypper

У курсі ми розглядаємо те, що спільне для всіх дистрибутивів — синтаксис bash, файлову ієрархію, системні виклики ядра — тому термін «ОС Linux» використовується без прив'язки до конкретного дистрибутиву.

⬡ Послідовність завантаження Linux

Від натискання кнопки увімкнення до bash-промпту проходить чітка послідовність етапів. Знати їх корисно для діагностики проблем (де саме зависло) і для розуміння файлів типу /boot/vmlinuz, /etc/fstab, /etc/systemd/system/.

1. BIOS / UEFI — прошивка плати робить POST (перевірку обладнання), знаходить завантажувальний пристрій. UEFI шукає EFI System Partition (FAT32) і файл .efi; BIOS читає перші 512 Б першого диска (MBR).
2. Завантажувач (GRUB) — читає свій конфіг (/boot/grub/grub.cfg), показує меню вибору ОС/ядра, завантажує в RAM ядро (vmlinuz-*) і initramfs.
3. Ядро Linux — розпаковує себе, ініціалізує драйвери (CPU, RAM, диск), монтує initramfs як тимчасову root-FS.
4. initramfs — мінімальна тимчасова FS у пам'яті: достатньо драйверів, щоб знайти і змонтувати справжню root-FS (з /etc/fstab або параметра root= у GRUB).
5. init / systemd — перший userspace-процес (PID 1). Запускає сервіси, монтує решту з fstab, переходить на graphical/multi-user target.
6. Login + сесія — getty / display manager → bash / GNOME → готовий до роботи.
Якщо щось пішло не так на етапі 5 — система впаде у emergency shell або rescue mode. Найчастіша причина: недоступний запис у /etc/fstab (зник UUID, диск зламаний). Прохід fstab при старті — головна причина радити в ньому UUID замість /dev/sdX. Формат /etc/fstab.
⬡ systemd і керування сервісами

systemd — сучасний менеджер сервісів у більшості дистрибутивів (Ubuntu, Debian, Fedora, Arch). Він — PID 1, запускає й моніторить усі фонові служби (демони). У Лаб. 2 ти запускатимеш SSH, NFS, cron — усі через systemctl.

Команда Що робить
systemctl status ssh Стан сервіса (running/stopped/failed) + останні логи
systemctl start ssh Запустити зараз
systemctl stop ssh Зупинити зараз
systemctl restart ssh Перезапустити (для перечитання конфіга)
systemctl reload ssh Перечитати конфіг без рестарту (якщо сервіс підтримує)
systemctl enable ssh Запускати при кожному завантаженні
systemctl disable ssh Не запускати при завантаженні
systemctl list-units --type=service Усі активні сервіси
journalctl -u ssh Логи конкретного сервіса
journalctl -f Слідкувати за логами в реальному часі

Конфігурація сервіса — unit file у /etc/systemd/system/ або /lib/systemd/system/. Приклад:

# /etc/systemd/system/myapp.service [Unit] Description=My background service After=network.target [Service] ExecStart=/usr/local/bin/myapp Restart=on-failure User=appuser [Install] WantedBy=multi-user.target

Після створення unit-файлу: sudo systemctl daemon-reload → sudo systemctl enable --now myapp.

⬡ Перші команди в терміналі

Запрошення командного рядка має формат користувач@хост:робочий_каталог$:

yurii@yurii-VirtualBox:~$
  • yurii — ім'я поточного користувача
  • yurii-VirtualBox — ім'я комп'ютера (hostname)
  • ~ — робочий каталог; символ ~ розгортається у домашній каталог користувача (для yurii це /home/yurii)
  • $ — кінець запрошення; для root буде #

Термінал — лише програма для текстового спілкування з оболонкою. Bash (Bourne Again SHell) — найпоширеніша оболонка в Linux: інтерпретує введені команди, запускає програми, забезпечує конвеєри й перенаправлення.

Ключова ідея. Усе в Linux — файл. Звичайні файли, каталоги, пристрої (/dev/sda), процеси (/proc/123), модулі ядра (/sys), сокети, канали — усе доступне через єдиний API open/read/write/close. Ця абстракція — фундамент усіх подальших розділів.
Що варто запам'ятати
  • ОС — посередник між програмами і апаратурою; виконує три ролі: менеджер ресурсів, абстрактна машина та захисник (ізоляція процесів і контроль прав).
  • Kernel mode vs user mode — апаратне розділення привілеїв. Прикладні програми не торкаються заліза напряму, а лише через системні виклики.
  • Linux — це ядро; Ubuntu, Mint, Fedora — це дистрибутиви (ядро + GNU-утиліти + менеджер пакетів).
  • Для лабораторних достатньо WSL (швидкий старт) або VirtualBox (повна графічна ВМ).
  • Ключова ідея для всього курсу: усе в Linux — файл (звичайні файли, пристрої, процеси, сокети).

⬡ Єдине дерево каталогів

На відміну від Windows, де кожен розділ диска має своє дерево (C:\, D:\, ...), у Linux існує одне дерево каталогів. Вершиною є корінь файлової системи — символ /. Усі диски, флешки, мережеві ресурси приєднуються до цього дерева через монтування (mount).

Каталог Призначення
/bin Системні програми (ls, cp, mv, ...)
/boot Конфігурації та файли завантаження системи (ядро, initrd, GRUB)
/dev Файли пристроїв (драйверів) — диски, термінали, нульовий пристрій
/etc Конфігурації системи та системних утиліт
/home Домашні каталоги користувачів — /home/yurii, /home/maria
/usr Програми користувача та бібліотеки
/tmp Тимчасові файли — видаляються при перезавантаженні
/root Домашній каталог суперкористувача
/media Точка автоматичного монтування зовнішніх пристроїв
/mnt Точка для монтування розділів користувачем (вручну)
/sys sysfs — файли модулів ядра та драйверів
/proc procfs — файли процесів і параметри ядра (/proc/sys)
/var Службовий каталог програм — конфігурації, log-файли, журнали
⬡ Абсолютні vs відносні шляхи
Тип Опис Приклад

Спеціальні позначення:

  • . — поточний (робочий) каталог
  • .. — батьківський каталог
  • ~ — домашній каталог поточного користувача
  • - (для cd -) — попередній робочий каталог
  • / — кореневий каталог
Розділювач рівнів: Linux — /, Windows — \. У шляхах Linux також враховується регістр: file.txt і File.txt — це різні файли.

⬡ Шаблони (globbing) та автодоповнення

Bash сам розгортає шаблони перед викликом команди:

Шаблон Збігається з Приклад
* Будь-яка послідовність символів ls 1* — усе, що починається з 1
? Один будь-який символ ls ?.c — однобуквені .c-файли
[abc] Один символ з набору ls [12].c
*.tmp Усе, що закінчується на .tmp rm *.tmp

Tab — автодоповнення імен файлів і команд. Подвійний Tab показує всі варіанти. ↑/↓ — історія команд. Ctrl+R — пошук у історії.

⬡ Файлові дескриптори та стандартні потоки

Кожна програма за замовчуванням має три відкриті файли — стандартні потоки. Унікальний номер цього «відкритого файлу» називається файловим дескриптором (fd).

fd Назва (UA) Назва (EN) За замовчуванням
0 Стандартне введення stdin Клавіатура
1 Стандартне виведення stdout Консоль
2 Стандартний потік помилок stderr Консоль

Функція printf у C та cout у C++ пишуть саме у fd=1.

⬡ Перенаправлення потоків

Bash дозволяє «прив'язати» потоки програми до файлів:

Оператор Дія Приклад
> stdout у файл (перезаписує) echo Hello > out.txt
>> stdout у файл (додає в кінець) echo World >> out.txt
< файл як stdin grep key < data.txt
2> stderr у файл ./prog 2> errors.log
&> або >file 2>&1 І stdout, і stderr у той самий файл ./prog &> all.log
# Записати вміст hello.txt і world.txt у greeting.txt, # а помилки (наприклад, відсутній файл) — у errors.log cat hello.txt world.txt name.txt > greeting.txt 2> errors.log
⬡ Конвеєри (pipes)

Конвеєр | з'єднує stdout однієї команди зі stdin іншої — без створення проміжного файлу:

команда_1 | команда_2 | команда_3

Конкретний приклад: знайти процеси, які містять «bash», і вивести 5 найперших:

ps aux | grep bash | head -n 5

Усередині ОС конвеєр реалізований через системний виклик pipe(), який створює пару file descriptors — один для запису, інший для читання. Деталі реалізації pipe().

⬡ Категорії користувачів і три права

У Linux кожен файл і кожен каталог мають права для трьох категорій користувачів:

  • u — user (власник файлу)
  • g — group (група, до якої належить файл)
  • o — other (всі решта)
  • a — all (одночасно u, g і o)

Кожна категорія може мати три типи прав:

Літера Назва Файл Каталог
r read Читати вміст Перераховувати вміст (ls)
w write Редагувати вміст Створювати/видаляти/перейменовувати файли
x execute Запускати як програму Заходити (cd) і доступатися до файлів усередині
⬡ Розшифровка ls -l

Перша колонка ls -l — 10 символів типу і прав:

drwxr-xr-x 3 yurii yurii 4096 Feb 14 14:33 lab_project │└─┬─┘└─┬─┘└─┬─┘ │ │ │ └─ права для інших (other) │ │ └────── права для групи (group) │ └─────────── права для власника (user/owner) └────────────── тип: d=каталог, -=звичайний файл, l=symlink, c=char device, b=block device, p=named pipe, s=socket

Інші колонки: кількість жорстких посилань, власник, група, розмір у байтах, дата модифікації, ім'я.

⬡ Числове (восьмеричне) представлення прав

Кожна трійка rwx кодується одним вісімковим числом (0-7) як трибітне число: r=4, w=2, x=1. Підсумовуємо. Числа на кшталт 755 або 644 — це вісімкові цифри; кожна цифра кодує 3 біти прав.

Вісімкове Двійкове Права Зміст
7 111 rwx Повний доступ
6 110 rw- Читання + запис
5 101 r-x Читання + виконання
4 100 r-- Лише читання
3 011 -wx Запис + виконання (рідко)
2 010 -w- Лише запис
1 001 --x Лише виконання
0 000 --- Жодного доступу
Приклад: rw- r-- --- → 6 4 0 → 640 (власнику читання+запис, групі читання, іншим нічого) rwx r-x r-x → 7 5 5 → 755 (типові права для каталогу або скрипта) rw- r-- r-- → 6 4 4 → 644 (типові права для звичайного файлу) rwx --- --- → 7 0 0 → 700 (приватний каталог користувача)
⬡ chmod — зміна прав

Дві форми синтаксису:

Форма Синтаксис Приклад
Символьна chmod кому ±/= права файл chmod o+w file.txt — додати запис іншим
Числова chmod NNN файл chmod 644 file.txt — встановити rw-r--r--
Рекурсивно chmod -R права каталог chmod -R 755 src/
# Додати право редагування іншим (символьно): sudo chmod o+w /home/temporary # Забрати читання і запис в інших: sudo chmod o-rw /home/temporary # Те саме числово (rw- r-- rw- → 646): sudo chmod 646 /home/temporary # Зробити скрипт виконуваним: chmod +x script.sh
⬡ SUID, SGID, sticky bit

Понад звичайні rwx існують три спеціальні біти, які кардинально змінюють поведінку. Видно у виводі ls -l як літери s або t на місці x.

Біт Вісімково Літера в ls -l Дія
SUID 4000 rws у owner Програма виконується від UID власника файлу, а не запускача
SGID (на файлі) 2000 rws у group Програма виконується з GID групи файлу, а не запускача
SGID (на каталозі) 2000 rws у group Нові файли всередині успадковують групу каталогу
Sticky 1000 rwt у other На каталозі: видалити файл може тільки його власник (навіть якщо w на каталог є)
# Класичні приклади: ls -l /usr/bin/passwd -rwsr-xr-x 1 root root ... /usr/bin/passwd # SUID — змінює пароль від root # (інакше звичайний user не міг би писати в /etc/shadow) ls -ld /tmp drwxrwxrwt 10 root root ... /tmp # sticky — кожен пише, але видаляє лише власник # Встановити: chmod 4755 /path/to/binary # SUID + 755 chmod u+s /path/to/binary # символьно chmod 2775 /path/to/dir # SGID на каталозі — для команди chmod 1777 /path/to/shared # sticky на каталозі
SUID — головний вектор привілейованих атак. Якщо знайти SUID-програму з вразливістю (buffer overflow, race condition), зловмисник отримує права власника. Тому SUID-біт треба ставити лише на ретельно перевірений код. Для своїх скриптів краще використовувати sudo з правилами в /etc/sudoers.
SUID на скрипті НЕ працює (з міркувань безпеки) — потрібен бінарний виконуваний файл. Скрипти треба обгорнути у бінарну C-обгортку.
⬡ umask — права за замовчуванням

umask — маска, яку ОС відмінусовує від базових прав при створенні файлу. Базові права: 666 для файлів, 777 для каталогів. Реальні права = базові & ~umask.

$ umask # дізнатись поточну 0022 # Розрахунок: # файл: 666 & ~022 = 666 & 755 = 644 → rw-r--r-- # каталог: 777 & ~022 = 777 & 755 = 755 → rwxr-xr-x # Змінити (на сесію): umask 0077 # файли тепер 600, каталоги 700 — приватніше touch test.txt ls -l test.txt # -rw------- (тільки власник) # Постійно — у ~/.bashrc або /etc/profile: echo 'umask 0027' >> ~/.bashrc

Типові значення: 022 — стандарт (group + other читають), 002 — у багатокористувацьких середовищах (group пише), 077 — параноя (нічого нікому).

⬡ Особливості прав каталогів
Права Що дає
--- Жодного доступу
--x Можна cd, але не видно списку файлів. Якщо знаєте точне ім'я — отримаєте до нього доступ
r-- Видно список (ls), але неможливо cd чи відкрити файли
r-x Базовий доступ: видно і можна заходити
rw- Видно список і можна змінювати, але неможливо заходити
rwx Повний доступ
Ключова ідея. Якщо у батьківського каталогу немає x, то навіть якщо у дочірнього всі права відкриті — ви до нього не дістанетесь. Метафора: дочірній каталог — кімната з відкритими дверима, але ви стоїте перед замкненими дверима будівлі.
Підступний нюанс. Право w на каталог дозволяє видалити будь-який файл усередині — навіть якщо у вас немає прав на сам файл. Видалення — це зміна каталогу, а не файлу.
⬡ Власник і група. chown

Власник файлу зазначений у 3-й колонці ls -l, група — у 4-й. Для одного файлу можна назначити будь-яку групу — це механізм для надання спільного доступу певному набору користувачів.

# Змінити власника: sudo chown yurii file.txt # Змінити власника і групу разом: sudo chown yurii:developers file.txt # Змінити лише групу: sudo chown :developers file.txt # Рекурсивно для всього каталогу: sudo chown -R yurii:yurii dir/

Тільки root може змінити власника файлу.

⬡ Суперкористувач (root) і sudo

root (UID=0) — обліковий запис із повним доступом до всього: створення користувачів, монтування дисків, встановлення пакетів, зміна власника будь-якого файлу. Два способи виконати дію від імені root:

Спосіб Команда Коли застосовувати
Перейти в root-режим sudo -i (і exit для виходу) Серія адмін-операцій
Одна команда як root sudo команда аргументи Точкова операція

У запрошенні root показується # замість $:

root@yurii-VirtualBox:~#
Каталог /root ≠ корінь /. Перший — домашня тека суперкористувача; другий — вершина файлової системи. Назва root однакова, але це різні поняття.
⬡ Робота з користувачами та групами
Команда Призначення
sudo adduser ім'я Інтерактивне створення користувача з домашнім каталогом і паролем
sudo useradd ім'я Низькорівневе створення (без інтерактивності)
sudo userdel ім'я Видалення користувача
sudo passwd ім'я Зміна пароля
su ім'я Перейти в сесію іншого користувача (потрібен його пароль)
sudo groupadd ім'я Створити групу
sudo usermod -aG group user Додати користувача до групи (-a — append, не перезаписувати)
groups [ім'я] Список груп користувача
cat /etc/passwd Список усіх користувачів
cat /etc/group Список усіх груп: ім'я:пароль:GID:список_користувачів
newgrp group Активувати нову групу для поточної сесії без перезавантаження
Виклична ідея. Group ≠ user. Створивши групу з тим самим іменем, що й у користувача (new_user), ви не робите її «приналежною» цьому користувачу. У Linux не існує поняття «група належить юзеру» — групи створюються, щоб збирати користувачів.
⬡ Worked example (Лаб. 1): спільний каталог для команди

Завдання: створити каталог, до якого матимуть доступ тільки члени певної групи.

# 1. Створити каталог від імені root sudo mkdir /home/lab_project # 2. Створити групу developers sudo groupadd developers # 3. Перевірити, чи створилась cat /etc/group | grep developers # 4. Додати користувачів до групи sudo usermod -aG developers yurii sudo usermod -aG developers new_user # 5. Призначити групу каталогу і дати їй право запису sudo chown :developers /home/lab_project sudo chmod g+w /home/lab_project # 6. У поточній сесії застосувати нову групу (без релогіну) newgrp developers # Тепер yurii і new_user можуть створювати файли в /home/lab_project
Що варто запам'ятати
  • 3×3 матриця прав: для (owner / group / other) × (read / write / execute). Кодується або символьно (rw-r--r--), або вісімково (644).
  • На каталозі x = можна зайти (cd), r = можна побачити список. Відсутність x у батьківського блокує усе всередині.
  • Видалити файл = змінити каталог, тому потрібен w на каталог, а не на сам файл.
  • sudo — для разових root-команд; sudo -i — для серій. Промпт # попереджає про root-режим.
  • usermod -aG group user додає у групу; -a обов'язкове (без нього перезаписує всі групи).

⬡ Що таке bash-сценарій

Сценарій (script) — це текстовий файл із послідовністю команд оболонки, виконуваних інтерпретатором bash. Файл починається з рядка shebang, який вказує ядру, яким інтерпретатором запускати файл:

#!/bin/bash # для bash-сценарію #!/usr/bin/python3 # для Python-сценарію #!/usr/bin/env bash # переносний варіант через PATH

Без shebang ядро спробує виконати файл як ELF-бінарник і отримає помилку.

⬡ Створення і запуск сценарію
  1. Створити файл (через nano, vim або touch+редактор):
    nano script.sh
  2. Додати shebang і команди:
    #!/bin/bash mkdir lab_1 cd lab_1 echo "Hello, world!" > hello.txt
  3. Зберегти (Ctrl+S, Ctrl+X у nano).
  4. Запустити одним із способів:
    bash script.sh # явним викликом інтерпретатора chmod +x script.sh # зробити виконуваним ./script.sh # запустити як виконуваний файл
Робоча директорія сценарію. За замовчуванням стартова робоча директорія сценарію — каталог, з якого його запустили (НЕ де він лежить). Тому або робіть cd на початку сценарію, або використовуйте абсолютні шляхи.

⬡ Змінні оточення (environment variables)

Змінні оточення — список іменованих значень, який ОС передає кожному запущеному процесу як неявні аргументи. Дочірні процеси успадковують оточення батька.

Змінна Призначення
USER Ім'я поточного користувача
HOME Домашній каталог (~)
HOSTNAME Назва комп'ютера
SHELL Шлях до оболонки користувача (наприклад, /bin/bash)
PATH Список каталогів через :, у яких система шукає виконувані файли
PWD Поточний робочий каталог
LANG Локаль (мова й кодування)
LD_LIBRARY_PATH Шлях для пошуку динамічних бібліотек (.so) — детально в розділі 7

⬡ export і час життя змінної

Без export змінна локальна для поточної оболонки. З export вона передається дочірнім процесам як змінна оточення.

FOO=bar # лише в цій оболонці export FOO=bar # передається дочірнім процесам unset FOO # видалити змінну

Час життя змінних, оголошених у командному рядку, — тривалість сесії термінала. При перезапуску термінала вони зникають.

Щоб змінна задавалася при кожному вході — додайте її у файл конфігурації оболонки:

Файл Коли виконується
~/.bashrc При відкритті інтерактивної оболонки (нового термінала)
~/.bash_profile або ~/.profile При логіні в систему
/etc/environment Системно для всіх користувачів
⬡ Доступ до оточення з C-програми

У C-програмі змінна оточення читається через бібліотечну функцію getenv:

#include <stdlib.h> #include <stdio.h> int main(void) { const char *path = getenv("PATH"); if (path) printf("PATH = %s\n", path); return 0; }

Третій параметр функції main у POSIX — char *envp[] — масив усіх змінних оточення.

⬡ Сортування і вибірка (Лаб. 1)

Корисні комбінації для аналізу виводу ls -l:

# Знайти найновіший файл у /home (сортування за часом) ls -l /home --sort=time | tail -n 1 # Знайти найстаріший (першим виводиться загальний обсяг — пропускаємо його) ls -l /home --sort=time | head -n 2 | tail -n 1 # Сортування за розміром ls -l /home --sort=size # Розмір каталогів (ls показує лише розмір метаданих) du -sh /home/*
Важливо. ls -l показує розмір файлу-каталогу як файлу метаданих (зазвичай 4096 байт — розмір блоку), а не сумарний розмір вмісту. Для реального розміру каталогу — du.
На іспит: shebang, command substitution $(...), різниця між ' і ", export для передачі дочірнім, життєвий цикл змінної оточення (зникає з закриттям термінала).
Що варто запам'ятати
  • Shebang #!/bin/bash у першому рядку говорить ядру, яким інтерпретатором запускати файл.
  • Команда vs файл: ./script.sh вимагає chmod +x; bash script.sh — ні.
  • $(...) — підстановка виводу команди; "$VAR" розгортає, '$VAR' — ні.
  • Локальна змінна існує лише в поточній оболонці; export VAR=... робить її змінною оточення для дочірніх процесів.
  • PATH — список каталогів через :, де bash шукає виконувані команди. which command показує, який саме файл буде запущений.

⬡ Як ОС бачить диски

У Linux кожен пристрій представлений файлом у /dev. Контролер SCSI/SATA/USB-Storage іменує диски символами sda, sdb, sdc ..., а NVMe — nvme0n1, nvme1n1. Розділи (partitions) — числовими суфіксами:

/dev/sda ← перший SATA-диск (фізичний пристрій) /dev/sda1 ← перший розділ цього диска /dev/sda2 ← другий розділ /dev/sdb ← другий диск (новостворений) /dev/sdb1 ← перший розділ диска sdb

⬡ Внутрішня будова файлової системи (ext4)

Розмічена область диска з ext4 поділена на блок-групи. Кожна група містить однакову внутрішню структуру:

Superblock — глобальні параметри ФС: розмір блоку, кількість блоків, журнал, ідентифікатор. Дублюється в кожній групі для відновлення.
Group Descriptor Table — де лежать наступні структури кожної групи (block bitmap, inode bitmap, inode table).
Block bitmap — бітова карта вільних/зайнятих блоків даних.
Inode bitmap + Inode table — карта вільних inode + сам масив inode-структур.
Data blocks — фактичний вміст файлів і каталогів.

Inode — структура з усіма метаданими файлу: розмір, права, власник, часи модифікації, посилання на блоки даних. Імені файлу в inode НЕМАЄ — імена зберігаються у каталогах (які теж файли) як пари (name, inode#). Це й уможливлює жорсткі посилання: кілька імен на той самий inode.

# Подивитись inode файлу $ ls -i /etc/passwd 1234567 /etc/passwd # Вміст inode $ stat /etc/passwd Size: 2841 Blocks: 8 IO Block: 4096 regular file Device: 803h/2051d Inode: 1234567 Links: 1 Access: (0644/-rw-r--r--) Uid: ( 0/ root) Gid: ( 0/ root) Access: 2026-05-08 09:11:23 Modify: 2026-05-01 14:33:01 Change: 2026-05-01 14:33:01 # Кількість inode на ФС обмежена — задається при mkfs $ df -i # перевірити inode usage Filesystem Inodes IUsed IFree IUse% Mounted on /dev/sda1 1310720 234567 1076153 18% /
Файлова система може закінчитися у inodes, навіть коли є вільне місце на диску — якщо створено мільйони крихітних файлів. Симптом: df -h показує вільне, touch повертає No space left on device. Лікування: подивитись df -i, видалити дрібнотню (наприклад, кеші).
⬡ Журналювання (journaling): чому ext4 переживає падіння

Раптове відключення живлення посеред запису може лишити ФС у некоректному стані: блок виділено в bitmap, але запис у inode не дописано. Після перезавантаження дані зіпсовані.

Рішення — журнал: окрема ділянка диска, куди ext4 спочатку записує намір («заплановано: виділити блок 12345 файлу inode 67»), потім виконує дію, і тільки тоді позначає журнальний запис як завершений. Якщо живлення вимкнулось посеред — після завантаження ext4 «програє» журнал і доводить операцію до кінця або відкатує.

Режим (mount option) Що журналюється Швидкість vs надійність
data=writeback Лише метадані; дані можуть потрапити у файл після оновлення метаданих Найшвидше, найменше гарантій — старі файли можуть з'явитись у нових позиціях
data=ordered (за замовч.) Метадані; дані пишуться перед метаданими Збалансовано: метадані завжди консистентні з даними
data=journal І метадані, і дані Найповільніше; повна консистентність

fsck.ext4 /dev/sdb1 — утиліта перевірки і відновлення (запускається автоматично при старті, якщо ФС несподівано демонтована або перевищено інтервал перевірок). У /etc/fstab остання колонка pass керує черговістю: 1 для root, 2 для інших, 0 — пропустити.

⬡ Монтування розділу

Монтування — приєднання вмісту розділу (його дерева каталогів) до основного дерева файлової системи в певній точці. Поки розділ не змонтовано, його вмісту немає в дереві каталогів.

# Ручне монтування sudo mount /dev/sdb1 /mnt # Перевірити монтування df -h lsblk # Розмонтувати sudo umount /mnt # або sudo umount /dev/sdb1

Опції монтування: -t ext4 (тип ФС), -o ro (read-only), -o rw (read-write).

⬡ Автоматичне монтування — /etc/fstab

Файл /etc/fstab описує постійні точки монтування — система обробляє їх при кожному завантаженні. Формат рядка:

device
mount point
fs type
options
dump
pass
# Локальний розділ ext4 /dev/sdb1 /mnt ext4 rw 0 0 # Або через UUID (рекомендовано — диски можуть змінювати літеру): UUID=a8f2-9cd1 /mnt ext4 defaults 0 2 # NFS-монтування (див. розд. 6): 192.168.1.1:/mnt/cloud /home/user/cloud nfs defaults 0 0

Колонки:

  • device — пристрій або UUID
  • mount point — каталог, у який монтуємо
  • fs type — ext4, xfs, ntfs, nfs, ...
  • options — defaults, rw, ro, noauto, ...
  • dump — чи робити dump (зазвичай 0)
  • pass — порядок перевірки fsck (1 для root, 2 для інших, 0 — пропустити)
⬡ Worked example (Лаб. 2): підключити новий 5 ГБ диск
  1. У VirtualBox: Налаштування ВМ → Пам'ять → Контролер SATA → +Диск (VDI, Pre-allocated, 5 ГБ)
  2. Запустити ВМ. Перевірити, що /dev/sdb з'явився:
    lsblk ls /dev/sd*
  3. Створити GPT і два розділи:
    sudo fdisk /dev/sdb # g → n → 1 → +2G → n → 2 → <Enter> → <Enter> → w
  4. Створити файлову систему ext4 на першому розділі:
    sudo mkfs.ext4 /dev/sdb1 lsblk -f
  5. Змонтувати у /mnt:
    sudo mount /dev/sdb1 /mnt df -h | grep sdb
  6. Зробити монтування постійним — додати рядок у /etc/fstab:
    sudo nano /etc/fstab # Додати в кінець: /dev/sdb1 /mnt ext4 rw 0 0
  7. Перевірити: створити файл, перезавантажити ВМ, переконатись, що файл лишився.
Чотири рівні абстракції диска: диск (/dev/sdb) → розділ (/dev/sdb1) → файлова система (ext4) → точка монтування (/mnt). Команди для кожного: fdisk, mkfs, mount, fstab.
Що варто запам'ятати
  • Чотири шари абстракції: блочний пристрій (/dev/sdb) → розділ (/dev/sdb1) → файлова система (ext4) → точка монтування (/mnt).
  • Сучасні системи використовують GPT (до 128 розділів, диски > 2 ТБ); MBR — legacy.
  • fdisk змінює таблицю в пам'яті програми — фізично записує лише w; q виходить без збереження.
  • mount приєднує ФС до каталогу-точки; /etc/fstab описує постійні монтування.
  • UUID краще, ніж /dev/sdX у fstab — порядок назв SD-дисків може змінитись між завантаженнями.

⬡ TCP-handshake і closed/listen/established

Перш ніж дані потечуть, TCP-сторони синхронізують номери послідовностей через three-way handshake:

Client Server | | | ────── SYN, seq=x ─────► | 1. Client каже "хочу з'єднання" | | | ◄────── SYN+ACK, seq=y, ack=x+1 | 2. Server: "ОК, мій seq=y, я отримав твій" | | | ────── ACK, ack=y+1 ─────► | 3. Client: "ОК, я отримав твій" | | | З'єднання ESTABLISHED — обмін даними

Аналогічно для розриву — four-way handshake з FIN і FIN+ACK.

Стани сокета (видно у ss -t): LISTEN (сервер чекає), SYN-SENT (клієнт послав SYN), SYN-RECV (сервер отримав SYN, послав SYN+ACK), ESTABLISHED (з'єднання активне), TIME-WAIT (після close — чекаємо 2*MSL ~60с, щоб упевнитись, що жоден пакет не загубився).

Чому SO_REUSEADDR. Якщо ти перезапускаєш сервер, попереднє з'єднання може бути в TIME_WAIT на тому ж порту — bind() поверне EADDRINUSE. Опція setsockopt(SO_REUSEADDR) дозволяє bind поверх TIME_WAIT. Завжди ставимо її в серверах.
⬡ Firewall: ufw та iptables

Без firewall будь-хто з мережі може підключитися до твого sshd, nfsd, postgresql. Firewall — фільтр у ядрі, що приймає чи блокує пакети за правилами.

В Ubuntu/Debian зручний фронт-енд — ufw (Uncomplicated Firewall), що під капотом використовує iptables/nftables:

# Дозволити SSH і ввімкнути firewall sudo ufw allow 22/tcp # або: sudo ufw allow ssh sudo ufw enable # Стан і правила sudo ufw status verbose # Дозволити NFS лише з конкретної підмережі sudo ufw allow from 192.168.56.0/24 to any port 2049 proto tcp # Заблокувати конкретну IP sudo ufw deny from 203.0.113.42 # Видалити правило sudo ufw delete allow 22/tcp # Відключити sudo ufw disable

iptables — низькорівневий інструмент для тонкого керування. У сучасних дистрибутивах поступово замінюється на nftables, але iptables -L — обов'язковий мінімум для адміна:

sudo iptables -L -v -n # показати всі правила sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT # додати правило sudo iptables -F # очистити (обережно — втратиш SSH!)
Перш ніж застосувати firewall на віддаленому сервері — переконайся, що SSH (22) явно дозволений. Інакше відключишся і не зможеш повернутись.
⬡ SSH — Secure Shell

SSH — протокол для безпечного віддаленого з'єднання з консоллю іншої машини. Шифрує весь трафік (асиметрична + симетрична криптографія). Слухає TCP-порт 22.

Компонент Машина Пакет

SSH-клієнт Та, з якої підключаються openssh-client (зазвичай уже є)

⬡ Автентифікація: пароль vs ключ

SSH підтримує два способи автентифікації:

Спосіб Принцип Безпека
Пароль Користувач вводить пароль при кожному підключенні Слабша; піддається brute-force
Ключі (RSA, ED25519) На клієнті — приватний ключ, на сервері — публічний. Сервер шифрує challenge публічним, клієнт розшифровує приватним Значно сильніша; стандарт для production
# Згенерувати пару ключів (на клієнті) ssh-keygen -t rsa # або сучасніше: ssh-keygen -t ed25519 # Файли: # ~/.ssh/id_rsa — приватний ключ (НІКОМУ не показувати!) # ~/.ssh/id_rsa.pub — публічний ключ (можна копіювати куди завгодно) # Скопіювати публічний ключ на сервер ssh-copy-id user@10.10.10.107 # Підключитись (тепер без пароля) ssh user@10.10.10.107 # Скопіювати файли через SSH (scp) scp file.txt user@10.10.10.107:/tmp/ scp -r dir/ user@10.10.10.107:/tmp/ # рекурсивно # Вийти з SSH-сесії exit
⬡ Налаштування SSH-сервера (Лаб. 2)
  1. Встановити сервер:
    sudo apt-get install openssh-server
  2. У /etc/ssh/sshd_config розкоментувати/змінити:
    PasswordAuthentication yes # дозволити пароль (для першого ssh-copy-id) PermitRootLogin no # заборонити root по SSH Port 22 # порт сервера
  3. Перезавантажити сервіс:
    sudo service sshd restart # або systemd-стиль: sudo systemctl restart sshd
Best practice: після встановлення ключів на сервері — поставте PasswordAuthentication no, щоб закрити пароль як вектор атаки.
⬡ NFS — Network File System

NFS — протокол спільного доступу до файлів через мережу. Дозволяє «змонтувати» каталог сервера як локальний на клієнті. Файли фізично знаходяться на сервері, але виглядають як частина файлової системи клієнта.

Клієнт · бачить /home/user/cloud як звичайний каталог
nfs-common на клієнті · перехоплює open/read/write
Мережа TCP/UDP (порт 2049) · RPC-виклики між клієнтом і сервером
nfs-kernel-server на сервері · виконує файлові операції
Файлова система сервера · /mnt/cloud на ext4
⬡ Налаштування NFS — сервер
  1. Встановити серверний пакет:
    sudo apt-get install nfs-kernel-server
  2. Створити каталог для шарингу:
    sudo mkdir -p /mnt/cloud
  3. У /etc/exports описати, що і кому експортувати:
    /mnt/cloud *(rw,sync,no_root_squash,no_subtree_check) # Або обмежити по IP: /mnt/cloud 10.10.10.108(rw,sync,no_root_squash,no_subtree_check)
  4. Опції:
    Опція Значення
    rw Дозволено читання і запис
    sync Синхронні запити (запис підтверджується після реального запису на диск)
    no_root_squash root клієнта залишається root на сервері (за замовчуванням стає nobody)
    no_subtree_check Не перевіряти, чи файл усе ще в експортованому піддереві
  5. Застосувати зміни:
    sudo exportfs -a sudo service nfs-kernel-server restart # Перевірити, що експортується showmount -e localhost
⬡ Налаштування NFS — клієнт
# Встановити клієнт sudo apt-get install nfs-common # Створити локальну точку монтування mkdir -p /home/user/cloud # Змонтувати папку з сервера sudo mount -t nfs <ip-сервера>:/mnt/cloud /home/user/cloud # Перевірити df -h | grep cloud # Тепер файли в /home/user/cloud — це фактично файли на сервері

Для постійного монтування — додати в /etc/fstab:

192.168.1.10:/mnt/cloud /home/user/cloud nfs defaults 0 0
⬡ cron — періодичні завдання

cron — демон для запуску команд за розкладом. Конфігурація — у двох місцях, з різним форматом рядка:

  • /etc/crontab та /etc/cron.d/* — системні; рядок має поле користувач (від чийого імені виконати): хв год день міс день_тиж користувач команда.
  • crontab -e — користувацький (зберігається у /var/spool/cron/crontabs/); без поля користувача (cron і так знає, чий це файл): хв год день міс день_тиж команда.
Часта помилка: скопіювати приклад з /etc/crontab у crontab -e разом з полем користувача. Cron сприйме ім'я користувача як першу частину команди — і мовчки нічого не виконає. Перевірка: grep CRON /var/log/syslog або journalctl -u cron.

Структура рядка /etc/crontab:

хв
год
день
місяць
день_тижня
користувач
команда
Поле Діапазон Опис
хвилини 0–59 * = кожна, 5 = на 5-й, */3 = кожні 3
години 0–23 так само
день_місяця 1–31 так само
місяць 1–12 так само
день_тижня 0–6 0=неділя, 1=понеділок, ... 6=субота

Приклади (формат /etc/crontab — з полем користувача):

# Кожні 3 хвилини */3 * * * * user /home/user/todo.sh # Щодня о 3:30 ранку 30 3 * * * user /home/user/backup.sh # Кожну годину рівно (0-та хвилина) 0 * * * * user /home/user/hourly.sh # Щопонеділка о 9:00 0 9 * * 1 user /home/user/weekly.sh # Перший день місяця о 0:00 0 0 1 * * user /home/user/monthly.sh

Ті самі приклади у crontab -e (без поля користувача):

*/3 * * * * /home/user/todo.sh 30 3 * * * /home/user/backup.sh 0 * * * * /home/user/hourly.sh 0 9 * * 1 /home/user/weekly.sh 0 0 1 * * /home/user/monthly.sh
⬡ Worked example (Лаб. 2): автоматичне резервне копіювання

Завдання: на сервері кожні 3 хв створювати tar.gz-архів каталогу /mnt/cloud у /mnt/backup, очищаючи старі архіви.

#!/usr/bin/bash # todo.sh — резервне копіювання # Записуємо дату створення резервної копії echo $(date) > /mnt/log # Розмір cloud echo "Cloud Size:" >> /mnt/log echo $(du -sh /mnt/cloud) >> /mnt/log # Назва архіву — дата і час створення name=$(date "+%d.%m.%y_%H_%M") # Створення архіву tar -czf /mnt/backup/$name.tar.gz /mnt/cloud # Видаляємо всі інші файли та архіви, крім нового cd /mnt/backup ls | grep -v $name | xargs rm -f cd - # Записуємо розмір новоствореної копії echo "Backup Size:" >> /mnt/log echo $(du -sh /mnt/backup/) >> /mnt/log
# Зробити виконуваним і додати в crontab chmod +x todo.sh sudo nano /etc/crontab # Додати рядок: */3 * * * * yurii /home/yurii/todo.sh # Перевірити (через кілька хвилин) ls -l /mnt/backup cat /mnt/log

Аналогічно — клієнт записує статистику свого CPU/RAM у спільну папку щохвилини:

#!/usr/bin/bash name=$(date "+%d.%m.%y_%H_%M") mpstat > /home/user/cloud/$name.log free >> /home/user/cloud/$name.log # crontab: * * * * * user /home/user/todo.sh
cron і середовище. Завдання cron виконуються з мінімальним оточенням (PATH часто короткий), тому використовуйте абсолютні шляхи у скриптах і явно встановлюйте PATH=... на початку, якщо потрібно.
На іспит: NFS = «диск через мережу», SSH = «віддалена консоль + захищений канал», cron — планувальник: формат /etc/crontab = хв год день міс день_тиж користувач команда; формат crontab -e — той самий без поля користувача.
Що варто запам'ятати
  • SSH-ключі: ssh-keygen -t ed25519, потім ssh-copy-id переносить публічний ключ на сервер. Приватний — ніколи нікому.
  • NFS робить віддалений каталог локально доступним через VFS — програма не знає, що файл на іншій машині.
  • /etc/exports на сервері описує, що і кому експортується; після зміни — exportfs -a.
  • Формат cron: у /etc/crontab — хв год день міс день_тиж користувач команда; у crontab -e — те саме без користувача. */3 * * * * = кожні 3 хвилини.
  • cron-середовище мінімальне — використовуй абсолютні шляхи в скриптах і явно встановлюй PATH=....

⬡ Чотири етапи побудови

З вихідного .c-файлу до виконуваного бінарника програма проходить чотири етапи. Перші три обробляють кожен файл окремо; четвертий (linking) збирає все разом.

1. Препроцесинг
cpp → .i
2. Компіляція
cc1 → .s
3. Асемблювання
as → .o
4. Лінкування
ld → ELF
Етап Що робить Вхід → вихід
1. Препроцесинг Текстові операції: розкриття #define, вставка #include, видалення коментарів .c → .i
2. Компіляція Перетворення коду C в асемблер. Найдовший етап .i → .s
3. Асемблювання Перетворення асемблерних інструкцій у двійковий код. Створює об'єктний файл .s → .o
4. Лінкування Об'єднання об'єктних файлів, додавання коду з бібліотек, проставляння адрес викликів .o+бібл. → ELF

Використовуючи gcc, можна зупинитись на будь-якому етапі:

gcc -E main.c -o main.i # 1: лише препроцесинг gcc -S main.c -o main.s # 1+2: до асемблера gcc -c main.c -o main.o # 1+2+3: до об'єктника (без лінкування) gcc main.c -o main # усі чотири етапи

⬡ Об'єктний файл — структура

Об'єктний файл (.o у Linux, .obj у Windows) — проміжний етап між компіляцією і повноцінним бінарником. Він містить машинні інструкції, але без проставлених адрес для викликів зовнішніх функцій і доступу до зовнішніх змінних.

Об'єктний файл містить службові секції, серед яких ключові дві:

Секція Що зберігає
Symbol Table (таблиця символів) Що цей файл надає: функції, глобальні змінні, оголошені тут — їхні імена та позиції
Relocation Block (таблиця переміщень) Що цей файл потребує: імена функцій і змінних, які тут викликаються, але визначені деінде
.text Машинні інструкції (виконуваний код)
.data Ініціалізовані глобальні змінні (зі значенням)
.bss Неініціалізовані глобальні змінні (нульові)
.rodata Read-only дані (рядкові літерали, константи)

На етапі лінкування компонувальник переглядає Symbol Tables усіх об'єктників, знаходить, хто надає те, що потрібно іншим, і проставляє правильні адреси у Relocation entries.

⬡ Огляд об'єктника — objdump

objdump — утиліта для розбору ELF/COFF-файлів. Корисні опції:

Опція Що показує
-d Дизасемблер: машинний код як інструкції асемблера
-t Symbol table
-r Relocation entries
-h Заголовки секцій
-x Усе разом
-s Hexdump кожної секції
gcc -c main.c -o main.o objdump -d main.o # дизасемблер objdump -t main.o # symbol table objdump -r main.o # relocations

Альтернативи: nm (тільки символи), readelf (всі секції ELF), strings (читабельні рядки).

⬡ Worked example (Лаб. 3): зовнішня функція і змінна

Файл main.c:

#include <stdio.h> int g_var = 0x222; // ВИЗНАЧЕНО тут (в .data) extern int f_var; // оголошено тут, ВИЗНАЧЕНО у іншому файлі int f_1(int a, int b); // лише прототип int main(void) { int a = g_var % f_var; int result = f_1(a, 2); return result; }

Файл f_1.c:

int f_var = 0x2; // ВИЗНАЧЕНО тут static int additional_function(int a) { // static — невидима ззовні return a * a; } int f_1(int a, int b) { return additional_function(a) / b; }

Ані файл main.c сам по собі, ані f_1.c сам по собі не є повноцінною програмою. Лише після лінкування вони збираються в один бінарник:

gcc -c main.c -o main.o # окрема компіляція кожного gcc -c f_1.c -o f_1.o gcc main.o f_1.o -o program # лінкування у програму ./program
⬡ Чому використовуються відносні адреси

Якщо запустити програму, її код потрапляє в оперативну пам'ять у деяку область, наперед невідому. Тому адреси викликів та доступу до глобальних змінних задаються відносно поточної інструкції (через регістр RIP), а не як абсолютні.

140001480: e8 1b 00 00 00 call 1400014a0 <f_1> # відн. зміщення +0x1b 140001485: 89 45 f8 mov %eax,-0x8(%rbp) ... 1400014a0: ... <f_1 starts here>

Розрахунок: 1400014a0 − 140001485 = 0x1b = 27. Чому береться адреса наступної інструкції (140001485), а не самої call? Тому що під час виконання call регістр команд RIP уже вказує на наступну інструкцію (це визначено в CPU pipeline).

Дві технології уникнення абсолютних адрес. 1) Віртуальна пам'ять — кожен процес «бачить» свій єдиний адресний простір (розглянемо в розд. 8). 2) Відносні адреси — зміщення від інструкції замість абсолюту. На сучасних 64-бітних системах (PIC — Position-Independent Code) це стандарт.

Властивість Статичне лінкування Динамічне лінкування

⬡ Створення статичної бібліотеки

Статична бібліотека — це просто архів об'єктних файлів (без стиснення). Створюється утилітою ar:

# Скомпілювати всі функції в .o gcc -c f_1.c -o f_1.o gcc -c f_2.c -o f_2.o # Створити архів-бібліотеку ar rsc libmymath.a f_1.o f_2.o # Опції ar: # r — replace (додати/замінити файли в архіві) # s — створити індекс (як ranlib) # c — створити архів, якщо не існує # Лінкувати з нашою програмою gcc main.o -L. -lmymath -o program # або просто: gcc main.o libmymath.a -o program # Опції gcc: # -L. — шукати бібліотеки в поточному каталозі # -lmymath — лінкувати libmymath.a (префікс lib і суфікс .a додаються автоматично)
⬡ Створення динамічної бібліотеки
# Скомпілювати з опцією PIC (Position-Independent Code) gcc -fPIC -c f_1.c -o f_1.o # Зібрати в .so gcc -shared f_1.o -o libdynamic.so # Лінкувати програму з посиланням на .so gcc main.o -L. -ldynamic -o program # Запустити (потрібно вказати, де шукати .so) export LD_LIBRARY_PATH=. ./program

-fPIC — генерувати позиційно-незалежний код (відносні адреси). Без цього .so не побудується (старі версії gcc виводили помилку; нові вимагають це за замовчуванням для shared).

Якщо програма не знаходить .so при запуску — помилка error while loading shared libraries: libdynamic.so: cannot open shared object file. Лінкер шукає в:

  • /lib, /usr/lib, /usr/local/lib — системні шляхи
  • Каталоги, перелічені у /etc/ld.so.conf та /etc/ld.so.conf.d/*
  • Каталоги зі змінної LD_LIBRARY_PATH
Дві ключові системні бібліотеки, які підвантажуються до КОЖНОЇ програми C: libc.so.6 (стандартна бібліотека C — printf, malloc, IO) і ld-linux-x86-64.so.2 (динамічний лінкер — він і завантажує всі решта .so).
⬡ Аналіз пам'яті процесу — pmap

Утиліта pmap показує, як використовується віртуальна пам'ять конкретного процесу:

# Запустити програму, що друкує свій PID і чекає ./program # у терміналі 1 # виводить: PID = 3197, чекає введення # У іншому терміналі: pmap -x 3197

Колонки: початкова адреса, розмір, RSS (фактично в пам'яті), Dirty, права (rwx), мапований об'єкт (файл або [anon]).

Область Призначення
r-x на бінарнику Секція .text — машинні інструкції
rw- на бінарнику Секція .data — глобальні змінні
rw--- [anon] мала Heap — куди malloc/new виділяють
rw--- [stack] Стек викликів функцій
libc.so.6 Динамічно завантажена libc
ld-linux.so Динамічний лінкер

RSS (Resident Set Size) — скільки реально займає в RAM. Kbytes — скільки зарезервовано. ОС може не одразу виділити фізичну пам'ять — лише при першому реальному зверненні.

Dirty — сторінка змінена відносно файлу-джерела й потребує запису назад. Чиста пам'ять (anon) не пов'язана з файлом і часто позначена dirty.

⬡ Віртуальна пам'ять: paging, TLB, page faults

Кожен процес «бачить» свій незалежний адресний простір — на x86-64 (4-рівневі таблиці, 48-бітні віртуальні адреси) це ≈ 128 ТБ для user-space (нижня половина) і ще ≈ 128 ТБ для ядра (верхня половина). Реальної RAM — на порядок менше. Як це працює?

Адресний простір процесу поділений на сторінки (4 КБ типово). Фізична RAM — на фрейми того ж розміру. Таблиця сторінок (page table) відображає віртуальні сторінки в фізичні фрейми. Перетворення робить апаратний блок CPU — MMU.

Віртуальна адреса (0x7f...abc) у твоєму коді
MMU + Page Table — апаратний lookup сторінки → фрейма
TLB — кеш переходів сторінка→фрейм (десятки записів у L1 dTLB/iTLB, ~1–2K у L2 STLB; інакше page-walk на кожне звернення — дорого)
Фізична адреса у RAM

Якщо запит на сторінку, якої немає у RAM — page fault. Ядро ловить його як виключення CPU і вирішує:

  • Minor fault: сторінка вже у RAM (наприклад, спільно з іншим процесом, або у page cache); просто оновити table → продовжити.
  • Major fault: сторінка на диску (mmap файла, swap); прочитати з диска у RAM (повільно: ~5 мс), оновити table, продовжити.
  • Invalid: процес зайшов у заборонену пам'ять — SIGSEGV.

⬡ Swap і OOM killer

Коли RAM закінчується, ядро витісняє рідковживані сторінки на диск — у спеціальний розділ або файл swap. Майбутній доступ до них викликає major page fault → читання з диска назад у RAM.

# Стан swap $ free -h total used free Mem: 7.7Gi 2.1Gi 3.4Gi Swap: 2.0Gi 128Mi 1.9Gi $ swapon --show NAME TYPE SIZE USED PRIO /swapfile file 2G 128M -2 # Створити swap-файл (для додавання) sudo fallocate -l 4G /swapfile sudo chmod 600 /swapfile sudo mkswap /swapfile sudo swapon /swapfile # Зробити постійним — додати в /etc/fstab: /swapfile none swap sw 0 0

swappiness (/proc/sys/vm/swappiness, 0–100) керує агресивністю витіснення. 60 — дефолт; знижують до 10–20 на десктопах із достатньо RAM.

Коли RAM повністю закінчилась і swap теж — ядро запускає OOM killer: вибирає процес з найбільшим oom_score (зазвичай — найбільший за пам'яттю) і вбиває його SIGKILL.

# Подивитись оцінку OOM: cat /proc/$PID/oom_score # від 0 до 1000 cat /proc/$PID/oom_score_adj # ваш bonus/penalty (-1000..1000) # Захистити критичний процес від OOM: sudo echo -1000 > /proc/$PID/oom_score_adj # фактично immortal # Логи OOM-event-ів: journalctl -k | grep -i 'killed process' dmesg | grep -i 'out of memory'
Чому процеси «загадково» зникають. Якщо твоя програма раптом завершилась без логів — перевір dmesg і journalctl -k на повідомлення «Out of memory: Killed process N». Це оом-кілер. Найчастіше — у пам'яті утік memory leak або просто std::vector не очікувано виріс.
⬡ Сторінки пам'яті

Сторінка (page) — мінімальна одиниця керування пам'яттю в Linux: 4 КБ на x86. Файли на диску мають логічні блоки по 4 КБ. Файл завжди займає пам'ять, заокруглену догори до кратного 4 КБ.

При читанні файлу ОС копіює сторінку з диска в спеціальну область RAM — page cache. Сторінки, які не використовуються довгий час, викидаються; гарячі — лишаються в кеші.

⬡ Як працює malloc (glibc): brk, mmap, arenas

Стандартний malloc — це не просто «попроси у ядра пам'ять». Кожен виклик у ядро (brk/mmap) дорогий, тому glibc реалізує свого внутрішнього менеджера. Розуміти його — критично для Лаб. 5 (свій thread-safe аллокатор).

Розмір запиту Що робить glibc
< 128 КБ Виділяє з arena (великого блоку, попередньо отриманого через brk). Поділяє на chunks через free-list.
≥ 128 КБ Окремий mmap прямо в ядрі. free повертає назад через munmap.

Ключові структури glibc:

  • Arena — велика суцільна ділянка віртуальної пам'яті. Головна арена росте через brk(); додаткові — через mmap(). Кожна арена має свій мютекс.
  • Chunk — одиниця виділення: метадані (8–16 байт перед користувацьким покажчиком) + дані. Розмір вирівняний до 16 байт.
  • Bins — масиви списків вільних chunk-ів за розмірами: fastbins (для крихітних, без об'єднання), small bins, large bins, unsorted bin.
  • Per-thread cache (tcache) — масив до 64 chunk-ів на потік без блокувань. Перший рівень кешу, дуже швидкий.
// Шлях malloc(64) у glibc: 1. Перевірити tcache того потоку ← O(1), без локів ↓ якщо порожній 2. Перевірити fastbins арени ← lock-free одна ітерація ↓ якщо порожній 3. Lock(arena) + перевірити small bins ↓ якщо порожній 4. Об'єднати suspicious chunks і пошук у large bins ↓ якщо нема відповідного 5. Розширити арену через brk() / новий mmap()

Багатопоточна оптимізація: за замовчуванням glibc створює до 8 * число_ядер арен; коли потік не може взяти лок головної — переходить на іншу. Це і робить malloc thread-safe «з коробки», ціною додаткової фрагментації.

Для Лаб. 5: твоя задача — повторити цей дизайн у спрощеному вигляді: окрема купа через mmap (не plain malloc), розбиття на chunks/bins, mutex (або, краще, lock-free через std::atomic) на free-list, опційно — per-thread arena через TLS. Скелет реалізації.
Корисно знати: brk() рухає кінець data-сегмента (heap росте монолітно вгору). mmap() анонімно мапить нову ділянку де завгодно у віртуальній пам'яті — більш гнучко, але дорожче по системних викликах.
⬡ Make — система збірки

Перекомпіляція кожного файлу при зміні одного — марнотратство. Make аналізує залежності між файлами і перекомпільовує лише те, що змінилось.

Файл Makefile описує цілі (targets) і залежності (dependencies). Синтаксис:

target: dependency_1 dependency_2 ... <TAB>recipe_command_1 <TAB>recipe_command_2
Важливо. Команди ОБОВ'ЯЗКОВО починаються з символу табуляції, не пробілів. Це найчастіша причина «загадкових» помилок Make.

Проста структура для збірки програми з трьох файлів:

Program_V_1: main.o F_1.o F_2.o <TAB>gcc main.o F_1.o F_2.o -o Program_V_1 main.o: main.c <TAB>gcc -c main.c -o main.o F_1.o: F_1.c <TAB>gcc -c F_1.c -o F_1.o F_2.o: F_2.c <TAB>gcc -c F_2.c -o F_2.o

Make перевіряє часові мітки: якщо main.c новіше за main.o, перекомпілює лише його, і потім перелінковує програму.

⬡ Запуск Make
Команда Дія
make Виконати першу ціль у Makefile (та її залежності)
make target Виконати конкретну ціль
make -f file Використати інший Makefile (за замовчуванням — Makefile)
make -j N Паралельне виконання N задач
make clean Звичайна користувацька ціль для очищення (видалення .o, бінарників)
⬡ Кілька варіантів збірки і ціль all/default

Якщо у Makefile задано кілька «верхніх» цілей, перша з них виконується за замовчуванням. Аби виконати всі — задайте узагальнену ціль:

all: Program_V_1 Program_V_2 Program_V_1: main.o F_1.o F_2.o <TAB>gcc main.o F_1.o F_2.o -o Program_V_1 Program_V_2: main.o libmymath.a <TAB>gcc main.o -L. libmymath.a -o Program_V_2 libmymath.a: F_1.o F_2.o <TAB>ar rsc libmymath.a F_1.o F_2.o

Тепер make зробить обидва варіанти, make Program_V_1 — лише перший.

⬡ Worked example (Лаб. 3): три цілі — default, static, dynamic
CC = gcc CFLAGS = -Wall -O2 # Псевдоцілі .PHONY: default static dynamic clean # default = просто три об'єктники + лінкування default: program program: main.o f_1.o f_2.o <TAB>$(CC) main.o f_1.o f_2.o -o program # static = статична бібліотека з функцій + main static: program_static libfuncs.a: f_1.o f_2.o <TAB>ar rsc libfuncs.a f_1.o f_2.o program_static: main.o libfuncs.a <TAB>$(CC) main.o -L. libfuncs.a -o program_static # dynamic = динамічна бібліотека dynamic: program_dynamic libfuncs.so: f_1.c f_2.c <TAB>$(CC) -fPIC -shared f_1.c f_2.c -o libfuncs.so program_dynamic: main.o libfuncs.so <TAB>$(CC) main.o -L. -lfuncs -o program_dynamic # Загальне правило: x.o з x.c %.o: %.c <TAB>$(CC) $(CFLAGS) -c $< -o $@ clean: <TAB>rm -f *.o *.a *.so program program_static program_dynamic
# Запуск make default # звичайна збірка make static # зі статичною бібліотекою make dynamic # з динамічною LD_LIBRARY_PATH=. ./program_dynamic make clean # очистити

Спеціальні змінні Make: $@ — ім'я цілі, $< — перша залежність, $^ — усі залежності, % — pattern (шаблон).

Що варто запам'ятати
  • Чотири стадії gcc: -E препроцесинг → -S компіляція → -c асемблювання → лінкування. Найдовша — компіляція.
  • Об'єктник містить Symbol Table (що надає) і Relocation Block (що потребує); лінкер з'єднує їх.
  • Статичне лінкування копіює бібліотеку у бінарник (великий, самодостатній). Динамічне — лише посилання (малий бінарник, спільний .so у RAM між процесами).
  • PIC (-fPIC) — обов'язковий для .so: код працює, де б його не завантажили в пам'ять.
  • Make: команди ОБОВ'ЯЗКОВО з табуляції; перевіряє часи модифікації і перебудовує лише застарілі цілі.

⬡ Що таке процес. PCB

Процес — це програма у виконанні: окремий простір адрес, набір відкритих файлів, контекст реєстрів CPU, поточний стан, права. Усю цю інформацію ядро тримає у структурі PCB (Process Control Block; у Linux — struct task_struct). Кожен процес має PID (Process ID), PPID (батьківський PID) і належить групі PGID.

PCB (struct task_struct у Linux) містить: pid_t pid, ppid, pgid, sid; # ідентифікатори uid_t uid, euid; # права long state; # R, S, D, Z, T struct mm_struct *mm; # таблиця сторінок, VM-області struct files_struct *files; # таблиця дескрипторів struct signal_struct *signal; # обробники сигналів struct sched_entity se; # дані планувальника struct task_struct *parent, *children; # дерево процесів

Процеси утворюють дерево: кожен процес (крім init/systemd з PID 1) має батька. fork() додає вузол; смерть процесу повідомляє батька через SIGCHLD.

⬡ Стани процесу

Планувальник переводить процес між станами. Класичні позначення з ps:

R
Running / runnable
S
Sleep (interruptible)
D
Sleep (uninterruptible) — IO
T
Stopped (SIGSTOP)
Z
Zombie

Zombie: процес завершився, але батько ще не викликав wait() — PCB лишається, бо в ньому код виходу. Orphan: батько помер раніше за дитину; дитину «всиновлює» init (PPID стає 1) і він робить wait(), коли вона завершиться.

⬡ Планування процесів: CFS, nice, priorities

На один CPU — мільйон бажаючих виконуватись. Планувальник (scheduler) вирішує: кого пускати наступним і на скільки. Linux із 2.6.23 використовує CFS (Completely Fair Scheduler).

Ідея CFS: відстежувати, скільки часу уже отримав кожен процес (vruntime); наступним пускати того, хто отримав найменше. Це дає справедливий розподіл — без часових слотів фіксованого розміру.

Клас планування Призначення Як налаштувати
SCHED_OTHER (CFS) Звичайні процеси (за замовч.) nice -n N command; renice
SCHED_FIFO Реальний час, без квантування — поки не звільнить CPU chrt -f priority command (потрібен root)
SCHED_RR Реальний час, round-robin із квантом chrt -r priority command
SCHED_IDLE Виконувати тільки коли CPU простоює chrt -i 0 command

nice — від -20 (найвищий пріоритет) до +19 (найнижчий). Default 0. Підняти пріоритет (від'ємне nice) — лише root. Знизити свій — кожен користувач.

⬡ fork(): створення процесу

fork() створює точну копію процесу, що його викликав. Дитина отримує копію адресного простору (на практиці — copy-on-write), копії дескрипторів і копію PCB зі своїм PID. У обох процесах виконання продовжується одразу після fork(); розрізнити їх — за поверненим значенням.

#include <unistd.h> #include <sys/types.h> pid_t fork(void); # Повертає: # у батьку — PID дитини (> 0) # у дитині — 0 # при помилці — -1 (errno: EAGAIN, ENOMEM)
#include <stdio.h> #include <unistd.h> #include <sys/wait.h> int main(void) { pid_t pid = fork(); if (pid < 0) { perror("fork"); return 1; } if (pid == 0) { // ----- дитина ----- printf("child: my pid=%d, ppid=%d\n", getpid(), getppid()); _exit(42); // _exit, а не exit, у дитині після fork } else { // ----- батько ----- int status; waitpid(pid, &status, 0); if (WIFEXITED(status)) printf("child returned %d\n", WEXITSTATUS(status)); } }
Що копіюється і що — ні. Копіюється: пам'ять (CoW), таблиця дескрипторів, обробники сигналів, поточний каталог, env, uid. Не копіюється: PID/PPID (нові), таймери (setitimer скидаються), pending-сигнали (порожні в дитині), мютекси у власному стані (тому fork у багатопотоковій програмі небезпечний).
⬡ exec(): запуск нової програми

Сам fork() робить копію; щоб запустити іншу програму, дитина викликає один з варіантів exec. Він заміщає адресний простір процесу новою програмою, зберігаючи PID, дескриптори (за замовчуванням), uid. Якщо exec* повертається — це помилка.

#include <unistd.h> extern char **environ; int execl (const char *path, const char *arg0, ..., NULL); int execlp(const char *file, const char *arg0, ..., NULL); int execle(const char *path, const char *arg0, ..., NULL, char *const envp[]); int execv (const char *path, char *const argv[]); int execvp(const char *file, char *const argv[]); int execve(const char *path, char *const argv[], char *const envp[]); // syscall # l = list (arg0, arg1, ..., NULL) v = vector (argv[]) # p = шукати в $PATH e = передати свій envp[] # execve — справжній системний виклик; решта — обгортки в libc
char *argv[] = {"ls", "-la", "/etc", NULL}; execvp(argv[0], argv); // шукає ls у $PATH perror("execvp"); // сюди потрапимо, лише якщо exec не вдалося

Шаблон fork+exec — основа кожної оболонки: батько форкає дитину, дитина робить exec, батько робить wait.

⬡ wait / waitpid: чекати на дитину
#include <sys/wait.h> pid_t wait(int *wstatus); pid_t waitpid(pid_t pid, int *wstatus, int options); # pid: > 0 — конкретна дитина # 0 — будь-яка дитина з тієї ж групи # -1 — будь-яка дитина (як wait) # < -1 — будь-яка дитина з групи |pid| # options: WNOHANG — не блокувати, якщо немає готових # WUNTRACED — повідомляти про SIGSTOP # WCONTINUED — повідомляти про SIGCONT # Макроси для розбору wstatus: WIFEXITED(s) — дитина вийшла нормально WEXITSTATUS(s) — код виходу (0..255) WIFSIGNALED(s) — вбита сигналом WTERMSIG(s) — який саме сигнал убив WIFSTOPPED(s) — призупинена (SIGSTOP)

Без wait мертва дитина залишається зомбі. Якщо батько не цікавиться кодом виходу, можна або встановити signal(SIGCHLD, SIG_IGN), або виставити SA_NOCLDWAIT через sigaction — тоді ядро автоматично прибирає зомбі.

⬡ Сигнали: модель і signal-safe

Сигнал — це асинхронне повідомлення процесу: «сталася подія, обробіть або термінуйте». Ядро доставляє сигнал, перериваючи нормальне виконання потоку і викликаючи обробник. Кожен процес має таблицю «сигнал → дія» (default / ignore / handler).

Сигнал № За замовчуванням Призначення
SIGINT 2 terminate Ctrl+C з термінала
SIGQUIT 3 core dump Ctrl+\
SIGKILL 9 terminate Не можна перехопити чи проігнорувати
SIGTERM 15 terminate Ввічливе завершення (default kill)
SIGSEGV 11 core dump Доступ до забороненої пам'яті
SIGCHLD 17 ignore Дитина завершилась/зупинилась
SIGSTOP 19 stop Не можна перехопити; жорстка пауза
SIGCONT 18 continue Продовжити після SIGSTOP
SIGALRM 14 terminate Спрацював таймер alarm()
SIGPIPE 13 terminate Запис у закритий pipe/socket
SIGUSR1/2 10/12 terminate Користувацькі сигнали
Async-signal-safe. Обробник сигналу може спрацювати посеред будь-якого коду. Тому в ньому дозволено викликати лише signal-safe функції: write, _exit, signal, sigaction, kill, read. printf, malloc, fprintf — не safe (можуть тримати внутрішній мютекс). Стандартний шаблон: у обробнику виставити volatile sig_atomic_t flag = 1;, а реакцію зробити в основному циклі.
⬡ sigaction(): сучасний API сигналів

signal() має історичні розбіжності між системами; стандартний спосіб — sigaction().

#include <signal.h> struct sigaction { void (*sa_handler)(int); // простий обробник void (*sa_sigaction)(int, siginfo_t *, void *); // розширений (з SA_SIGINFO) sigset_t sa_mask; // блокувати ці сигнали під час обробки int sa_flags; // SA_RESTART, SA_SIGINFO, SA_NOCLDWAIT, ... void (*sa_restorer)(void); // не використовувати }; int sigaction(int signum, const struct sigaction *act, struct sigaction *oldact);
#include <signal.h> #include <stdio.h> #include <string.h> #include <unistd.h> static volatile sig_atomic_t stop = 0; static void on_int(int sig) { stop = 1; // лише прапор! const char msg[] = "\nbye\n"; write(STDOUT_FILENO, msg, sizeof msg - 1); } int main(void) { struct sigaction sa; memset(&sa, 0, sizeof sa); sa.sa_handler = on_int; sigemptyset(&sa.sa_mask); sa.sa_flags = SA_RESTART; // авто-перезапуск перерваних syscall if (sigaction(SIGINT, &sa, NULL) == -1) { perror("sigaction"); return 1; } while (!stop) { // основний цикл; sleep(1) автоматично перезапуститься завдяки SA_RESTART sleep(1); } return 0; }

Ключові прапори: SA_RESTART — перерваний сигналом syscall перезапуститься, а не поверне EINTR; SA_SIGINFO — використовуй sa_sigaction з розширеною інформацією (PID відправника, причина); SA_NOCLDWAIT — не лишати зомбі від дітей.

⬡ kill / raise: надіслати сигнал
#include <signal.h> int kill(pid_t pid, int sig); int raise(int sig); // = kill(getpid(), sig) # pid: > 0 — конкретний процес # 0 — усій своїй групі # -1 — усім, кому маємо право # < -1 — групі з PGID = |pid| # sig = 0 — перевірка існування процесу без дії # Команда: kill -SIGTERM 1234 або kill -15 1234 # kill -KILL -1234 # по групі
⬡ pipe(): однонапрямний канал

pipe() створює пару дескрипторів, що з'єднані ядерним кільцевим буфером: fd[0] — для читання, fd[1] — для запису. Класично використовується між спорідненими процесами (батько+дитина) — після fork() обидва бачать ту саму пару.

#include <unistd.h> int pipe(int fd[2]); // fd[0] = read, fd[1] = write int dup(int oldfd); // дублює дескриптор у найменший вільний int dup2(int oldfd, int newfd); // дублює в задане число; закриває newfd, якщо відкритий # Семантика: # запис у fd[1], коли всі fd[0] закриті → SIGPIPE / EPIPE # читання з fd[0], коли всі fd[1] закриті → 0 (EOF)
Закривайте незадіяні кінці. Якщо батько використовує лише читання, він закриває fd[1]; інакше дитина ніколи не отримає EOF, бо «десь у системі» залишається відкритий записувальний кінець.
⬡ Lab 4: myshell — fork + pipe + dup2 + exec

Класичний шаблон оболонки: щоб запустити cmd1 | cmd2, треба запустити дві дитини, з'єднані каналом, і перенаправити їхні stdout/stdin у канал через dup2.

// myshell: виконує "ls -la | wc -l" #include <stdio.h> #include <unistd.h> #include <sys/wait.h> int main(void) { int p[2]; pipe(p); pid_t a = fork(); if (a == 0) { // дитина 1: ls -la, stdout → pipe dup2(p[1], STDOUT_FILENO); close(p[0]); close(p[1]); execlp("ls", "ls", "-la", NULL); perror("ls"); _exit(127); } pid_t b = fork(); if (b == 0) { // дитина 2: wc -l, stdin ← pipe dup2(p[0], STDIN_FILENO); close(p[0]); close(p[1]); execlp("wc", "wc", "-l", NULL); perror("wc"); _exit(127); } // батько: закрити обидва кінці, дочекатись дітей close(p[0]); close(p[1]); waitpid(a, NULL, 0); waitpid(b, NULL, 0); return 0; }

Хто не закриє свій кінець каналу — заблокує EOF. Тому правило: після dup2 закривай оригінальні дескриптори.

⬡ popen / pclose: спрощений варіант

Для одного pipe-з'єднання з підпроцесом libc дає обгортку:

#include <stdio.h> FILE *popen(const char *command, const char *type); // type: "r" або "w" int pclose(FILE *stream); // повертає wstatus або -1 # Внутрішньо: pipe + fork + dup2 + execve("/bin/sh", "-c", command) FILE *f = popen("ls -la /etc", "r"); char buf[256]; while (fgets(buf, sizeof buf, f)) fputs(buf, stdout); int status = pclose(f); // не забути!

Зручно, але через /bin/sh -c; не передавайте сюди недовірений рядок (shell injection).

⬡ Іменовані канали (FIFO): pipe між неспорідненими процесами

Звичайний pipe() працює лише між спорідненими процесами (батько+дитина). Іменований канал (FIFO) — той самий механізм, але доступний як файл у файловій системі; будь-які два процеси можуть його відкрити за іменем.

# З оболонки: mkfifo /tmp/myfifo # створити FIFO # Термінал 1 (читач): cat /tmp/myfifo # блокується, поки хтось не запише # Термінал 2 (писач): echo "hello" > /tmp/myfifo # розблоковує читача ls -l /tmp/myfifo prw-r--r-- 1 user user 0 May 9 12:00 /tmp/myfifo │ └─ 'p' = named pipe

З C — як звичайний файл:

#include <sys/stat.h> #include <fcntl.h> int mkfifo(const char *pathname, mode_t mode); // 0 при успіху, -1 з errno // Писач: mkfifo("/tmp/myfifo", 0666); int fd = open("/tmp/myfifo", O_WRONLY); // блокується, поки нема читача write(fd, "data", 4); close(fd); // Читач (інший процес): int fd = open("/tmp/myfifo", O_RDONLY); // блокується, поки нема писача char buf[16]; read(fd, buf, sizeof buf); close(fd);

FIFO добре підходить для простих локальних pipeline'ів, де процеси запускаються незалежно (наприклад, один daemon пише, інший читає). Для двонаправленого зв'язку — два FIFO або сокет AF_UNIX.

⬡ System V IPC: shared memory, message queues, semaphores

System V IPC — старший набір механізмів IPC, який існує з 1980-х. Він не на основі дескрипторів — використовує ID, отримані через ftok()+*get. У сучасному коді частіше використовують POSIX-аналоги, але на іспиті можуть запитати.

Механізм Sys V API POSIX-аналог
Shared memory shmget, shmat, shmdt, shmctl shm_open + mmap
Message queue msgget, msgsnd, msgrcv, msgctl mq_open, mq_send, mq_receive
Semaphore semget, semop, semctl sem_open, sem_wait, sem_post

Shared memory — найшвидший IPC: ділянка пам'яті мапиться у адресні простори двох (чи більше) процесів і вони пишуть/читають напряму, без копіювання через ядро. Швидкість — як у звичайної пам'яті; ціна — потрібна синхронізація вручну (мютекс у тій же shm, або семафор).

// POSIX shared memory + mmap (рекомендований сучасний спосіб) #include <sys/mman.h> #include <fcntl.h> #include <unistd.h> // Виробник: int fd = shm_open("/mydata", O_CREAT | O_RDWR, 0600); ftruncate(fd, sizeof(int) * 1024); int *arr = mmap(NULL, sizeof(int) * 1024, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0); arr[0] = 42; // тепер видно в інших процесах // Споживач (інший процес): int fd = shm_open("/mydata", O_RDONLY, 0); int *arr = mmap(NULL, sizeof(int) * 1024, PROT_READ, MAP_SHARED, fd, 0); printf("%d\n", arr[0]); // 42 // Прибрати: shm_unlink("/mydata"); // видалити з /dev/shm

POSIX shm-об'єкти видно як файли у /dev/shm/. Команди керування Sys V IPC: ipcs (список), ipcrm (видалити).

Огляд механізмів IPC: pipe (споріднені, потоковий), FIFO (неспоріднені, потоковий), socket (мережа або локально, двонаправлений), shared memory (найшвидший, треба синхронізація), signal (одностороннє повідомлення без даних), message queue (повідомлення з пріоритетами).
⬡ Сокети: AF_UNIX і AF_INET

Pipe працює лише між спорідненими процесами на одній машині. Сокети — універсальний механізм: між неспорідненими процесами (AF_UNIX) або через мережу (AF_INET, AF_INET6).

#include <sys/socket.h> #include <sys/un.h> // AF_UNIX #include <netinet/in.h> // AF_INET #include <arpa/inet.h> // inet_pton, htons int socket(int domain, int type, int protocol); # domain: AF_UNIX (локально) | AF_INET (IPv4) | AF_INET6 # type: SOCK_STREAM (TCP) | SOCK_DGRAM (UDP) # protocol: 0 = за замовчуванням int bind (int s, const struct sockaddr *addr, socklen_t len); int listen (int s, int backlog); int accept (int s, struct sockaddr *addr, socklen_t *len); // блокується int connect(int s, const struct sockaddr *addr, socklen_t len); ssize_t send(int s, const void *buf, size_t n, int flags); ssize_t recv(int s, void *buf, size_t n, int flags); int close (int s);
SERVER: socket() → bind() → listen() → accept() → recv()/send() → close()
CLIENT: socket() → connect() → send()/recv() → close()

AF_UNIX ідентифікує точку шляхом у файловій системі (/tmp/myapp.sock) — швидко, без мережевого стека, обмежено межами однієї машини. AF_INET ідентифікує точку парою (IP, port) — працює через мережу.

⬡ Простий TCP-сервер (Lab 4 webshell)
#include <stdio.h> #include <string.h> #include <unistd.h> #include <arpa/inet.h> #include <sys/socket.h> int main(void) { int s = socket(AF_INET, SOCK_STREAM, 0); int yes = 1; setsockopt(s, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof yes); struct sockaddr_in addr; memset(&addr, 0, sizeof addr); addr.sin_family = AF_INET; addr.sin_addr.s_addr = htonl(INADDR_ANY); // 0.0.0.0 addr.sin_port = htons(8080); bind(s, (struct sockaddr*)&addr, sizeof addr); listen(s, 16); for (;;) { struct sockaddr_in cli; socklen_t clen = sizeof cli; int c = accept(s, (struct sockaddr*)&cli, &clen); if (c < 0) continue; char buf[1024]; ssize_t n = recv(c, buf, sizeof buf - 1, 0); if (n > 0) { buf[n] = 0; // ... обробка HTTP-запиту ... const char *resp = "HTTP/1.1 200 OK\r\n" "Content-Type: text/plain\r\n" "Content-Length: 5\r\n" "\r\n" "hello"; send(c, resp, strlen(resp), 0); } close(c); } }

Це послідовний сервер: один клієнт одночасно. Щоб обслуговувати багатьох — або fork/pthread на кожне з'єднання, або (краще) poll/epoll у одному потоці (див. розділ 9).

⬡ Групи процесів і таймаут (Lab 4)

Кожен процес належить групі (PGID). Усі процеси одного pipeline у shell зазвичай мають однаковий PGID — тому Ctrl+C (SIGINT) із термінала доставляється усім. Сигнал на групу: kill(-pgid, SIGTERM).

#include <unistd.h> int setpgid(pid_t pid, pid_t pgid); // pgid=0 → новий PGID = pid // Lab 4: запустити команду з лімітом часу через SIGALRM #include <signal.h> #include <sys/wait.h> pid_t kid; void on_alarm(int s) { kill(-kid, SIGKILL); } // вбити всю групу int main(int argc, char **argv) { int timeout_sec = atoi(argv[1]); kid = fork(); if (kid == 0) { setpgid(0, 0); // дитина — лідер нової групи execvp(argv[2], &argv[2]); _exit(127); } setpgid(kid, kid); // race-safe з боку батька signal(SIGALRM, on_alarm); alarm(timeout_sec); int st; waitpid(kid, &st, 0); }
Контрольні запитання: Що повертає fork() у батьку, дитині, при помилці? Чим зомбі відрізняється від сироти і хто їх «прибирає»? Який сигнал не можна перехопити? Що робить SA_RESTART? Чому після dup2 треба закрити оригінал? Різниця між AF_UNIX і AF_INET? Послідовність системних викликів TCP-сервера?
Що варто запам'ятати
  • fork() повертає двічі: 0 у дитини, PID дитини у батька, -1 при помилці.
  • Шаблон оболонки: fork() → у дитині execvp() → у батька waitpid(). Без wait — зомбі.
  • Два невідбивані сигнали: SIGKILL (9) і SIGSTOP (19). Усі решта можна перехопити через sigaction.
  • У обробнику сигналу — лише async-signal-safe функції. printf, malloc — НЕ безпечні. Шаблон: volatile sig_atomic_t flag.
  • Конвеєр cmd1 | cmd2 = pipe() + два fork() + dup2() кінців у stdin/stdout + execvp().

⬡ Потік vs процес

Потік — окрема одиниця виконання усередині процесу: свій стек, свій набір реєстрів, свій PC, але спільні з іншими потоками: куча (heap), глобальні змінні, дескриптори, обробники сигналів. Тому потоки дешеві (немає копіювання адресного простору) і небезпечні (треба самому захищати спільні дані).

Спільне між потоками
код, heap, globals, fd-таблиця, обробники сигналів, cwd
Своє у потока
стек, реєстри, errno, маска сигналів, TLS

У Linux потоки — це звичайні задачі ядра з прапорцями CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_SIGHAND: ядро не розрізняє «потік» і «процес», розрізняє лише, що з ким спільне.

⬡ Race condition і потреба синхронізації

Якщо два потоки записують одну змінну без синхронізації — результат непередбачуваний. Класичний приклад: x++ — це читання + інкремент + запис, три інструкції. Перемикання потоку між ними губить інкременти.

int counter = 0; // 1 000 000 інкрементів × 4 потоки void *inc(void *_) { // очікуємо: 4 000 000 for (int i = 0; i < 1000000; i++) counter++; return NULL; } // Реально отримуємо ~1 200 000–2 800 000. ← Race!

Інструменти, що це лікують: mutex (взаємне виключення), atomic (неподільні операції на одному слові), condition variable (чекати на подію), semaphore (рахункова синхронізація), read-write lock (багато читачів, один записувач).

⬡ Mutex: pthread і std::mutex
#include <pthread.h> int pthread_mutex_init (pthread_mutex_t *m, const pthread_mutexattr_t *a); int pthread_mutex_lock (pthread_mutex_t *m); // блокується int pthread_mutex_trylock(pthread_mutex_t *m); // EBUSY якщо зайнятий int pthread_mutex_unlock (pthread_mutex_t *m); int pthread_mutex_destroy(pthread_mutex_t *m); pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER; // статична ініціалізація long counter = 0; void *inc(void *_) { for (int i = 0; i < 1000000; i++) { pthread_mutex_lock(&mu); counter++; pthread_mutex_unlock(&mu); } return NULL; }
// C++: RAII — std::lock_guard сам зніме lock при виході з області #include <mutex> std::mutex m; long counter = 0; void inc() { for (int i = 0; i < 1000000; i++) { std::lock_guard<std::mutex> g(m); // lock у конструкторі counter++; } // unlock у деструкторі — навіть при exception } // Для умовних/складних схем — std::unique_lock (можна lock/unlock вручну)
Deadlock виникає, коли два потоки беруть мютекси у різному порядку (T1: A→B, T2: B→A). Лікування: єдиний глобальний порядок захоплення. У C++ — std::lock(m1, m2) атомарно бере обидва.
⬡ Condition variable: чекати на подію

Mutex захищає дані; CV дає змогу пасивно чекати, поки інший потік не виставить умову. Шаблон producer-consumer:

#include <pthread.h> int pthread_cond_init (pthread_cond_t *c, const pthread_condattr_t *a); int pthread_cond_wait (pthread_cond_t *c, pthread_mutex_t *m); // атомарно: unlock(m)+sleep, при wake — lock(m) int pthread_cond_timedwait(pthread_cond_t *c, pthread_mutex_t *m, const struct timespec *t); int pthread_cond_signal (pthread_cond_t *c); // розбудити одного int pthread_cond_broadcast(pthread_cond_t *c); // розбудити всіх
pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER; pthread_cond_t cv = PTHREAD_COND_INITIALIZER; queue_t q; bool done = false; void *producer(void *_) { while (have_more()) { pthread_mutex_lock(&mu); push(&q, next_item()); pthread_cond_signal(&cv); // розбудити одного консьюмера pthread_mutex_unlock(&mu); } pthread_mutex_lock(&mu); done = true; pthread_cond_broadcast(&cv); pthread_mutex_unlock(&mu); return NULL; } void *consumer(void *_) { for (;;) { pthread_mutex_lock(&mu); while (empty(&q) && !done) // ЗАВЖДИ while, не if (spurious wakeup) pthread_cond_wait(&cv, &mu); if (empty(&q) && done) { pthread_mutex_unlock(&mu); return NULL; } item = pop(&q); pthread_mutex_unlock(&mu); process(item); } }

У C++: std::condition_variable + std::unique_lock<std::mutex>. Метод cv.wait(lk, []{ return ready; }); сам закладає цикл і захист від spurious wakeup.

⬡ Atomic і моделі пам'яті

Mutex дорогий: системний виклик при суперечці. Для одного слова часто досить атомарної операції — CPU виконує її як одну неподільну інструкцію (LOCK XADD, CAS).

#include <atomic> // C++ #include <stdatomic.h> // C11 std::atomic<long> counter{0}; void inc() { for (int i = 0; i < 1000000; i++) counter.fetch_add(1, std::memory_order_relaxed); } // Базові операції: load, store, exchange, fetch_add/sub/and/or/xor, // compare_exchange_weak / _strong (CAS) // memory_order: // relaxed — лише атомарність, без впорядкування // acquire — після цього load усе пізніше не «переїде» вгору // release — до цього store усе раніше не «переїде» вниз // acq_rel — для read-modify-write // seq_cst — глобальний порядок (за замовчуванням, найдорожчий)
// CAS-цикл (compare-and-swap): «змінити, якщо ніхто не змінив раніше» std::atomic<Node*> head; void push(Node *n) { Node *old; do { old = head.load(std::memory_order_relaxed); n->next = old; } while (!head.compare_exchange_weak( old, n, std::memory_order_release, // успіх std::memory_order_relaxed)); // невдача }

compare_exchange_weak може давати «фальшиві провали» (cheap, у циклі), _strong — без них (ціна більша). У циклі завжди weak.

⬡ Lock-free структури

Lock-free алгоритм гарантує, що хтось із потоків завжди просувається, навіть якщо інший зупинився посеред операції. Класична реалізація — на CAS-циклі.

Wait-free — кожен потік завершує операцію за обмежене число кроків (найсильніша гарантія, рідко в практиці)
Lock-free — система як ціле просувається; якийсь потік завжди успіх (CAS-loop)
Obstruction-free — потік завершує, якщо тимчасово сам
Lock-based — мютекс; будь-який блокує усіх

ABA-проблема: значення A змінили на B і назад на A; CAS бачить «незмінилось», але стан інший. Лікування — теговані вказівники (CAS на пару (ptr, version)) або hazard pointers / RCU для безпечного звільнення пам'яті.

Lock-free не означає «швидше»: під слабкою суперечкою mutex дешевший. Lock-free виграє при високій конкуренції і великій кількості ядер.

⬡ Semaphore
#include <semaphore.h> int sem_init (sem_t *s, int pshared, unsigned value); int sem_wait (sem_t *s); // декрементує; блокується, якщо 0 int sem_trywait(sem_t *s); // EAGAIN якщо 0 int sem_post (sem_t *s); // інкрементує; будить одного waiter int sem_destroy(sem_t *s); # value=1 → бінарний (≈ mutex без поняття «власника») # value=N → лімітує паралелізм (наприклад, N слотів пулу)

На відміну від mutex, у семафора немає власника: sem_post може робити інший потік, ніж sem_wait. Тому семафор — стандартний інструмент сигналізації між потоками і безпечний у обробниках сигналів (sem_post — async-signal-safe).

⬡ Lab 5: thread-safe аллокатор

Стандартний malloc уже потокобезпечний (під капотом — мютекс + arena per-CPU у glibc). Лабораторне завдання — реалізувати власний allocator, що:

  • тримає список вільних блоків (free-list) — щоб уникати дорогого brk/mmap на кожне виділення;
  • захищає free-list мютексом, або
  • тримає per-thread arena (TLS) — без блокувань на швидкому шляху;
  • повертає блоки великих розмірів напряму у mmap, малі — з арени.
// Скелет per-arena allocator. У реальному коді — power-of-two size classes. #include <stddef.h> #include <sys/mman.h> #include <pthread.h> typedef struct Block { struct Block *next; size_t size; } Block; typedef struct { pthread_mutex_t mu; Block *free_list; } Arena; static __thread Arena *my_arena; // TLS: своя арена в кожного потоку void *my_malloc(size_t n) { Arena *a = my_arena; pthread_mutex_lock(&a->mu); Block **pp = &a->free_list; while (*pp && (*pp)->size < n) pp = &(*pp)->next; Block *b = *pp; if (b) { *pp = b->next; pthread_mutex_unlock(&a->mu); return b + 1; } pthread_mutex_unlock(&a->mu); size_t total = sizeof(Block) + n; b = mmap(NULL, total, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0); b->size = n; return b + 1; } void my_free(void *p) { if (!p) return; Block *b = (Block*)p - 1; Arena *a = my_arena; pthread_mutex_lock(&a->mu); b->next = a->free_list; a->free_list = b; pthread_mutex_unlock(&a->mu); }
// C++: перевизначити operator new / delete для всього процесу #include <new> #include <cstdlib> void *operator new(std::size_t n) { void *p = my_malloc(n); if (!p) throw std::bad_alloc(); return p; } void operator delete(void *p) noexcept { my_free(p); } void *operator new[](std::size_t n) { return ::operator new(n); } void operator delete[](void *p) noexcept{ ::operator delete(p); }
⬡ Thread pool

Створення потоку — недешеве. Якщо роботи багато і вона коротка, тримай пул готових потоків і годуй їх задачами через захищену чергу.

// Спрощений thread pool на pthread + черга задач typedef void (*task_fn)(void*); typedef struct { task_fn f; void *arg; } Task; typedef struct { pthread_t *workers; int n; Task *q; // кільцевий буфер int cap, head, tail, count; pthread_mutex_t mu; pthread_cond_t not_empty, not_full; bool stop; } Pool; void *worker(void *arg) { Pool *p = arg; for (;;) { pthread_mutex_lock(&p->mu); while (p->count == 0 && !p->stop) pthread_cond_wait(&p->not_empty, &p->mu); if (p->count == 0 && p->stop) { pthread_mutex_unlock(&p->mu); return NULL; } Task t = p->q[p->head]; p->head = (p->head + 1) % p->cap; p->count--; pthread_cond_signal(&p->not_full); pthread_mutex_unlock(&p->mu); t.f(t.arg); // виконуємо БЕЗ замка } } void pool_submit(Pool *p, task_fn f, void *arg) { pthread_mutex_lock(&p->mu); while (p->count == p->cap) pthread_cond_wait(&p->not_full, &p->mu); p->q[p->tail] = (Task){f, arg}; p->tail = (p->tail + 1) % p->cap; p->count++; pthread_cond_signal(&p->not_empty); pthread_mutex_unlock(&p->mu); }

Розмір пулу зазвичай беруть ≈ std::thread::hardware_concurrency() для CPU-bound задач і помітно більше — для IO-bound (більшість потоків блокуються в read).

⬡ Blocking vs non-blocking IO

За замовчуванням read/recv/accept блокуються, поки немає даних. Це нормально для одного клієнта; для тисяч — катастрофа (тисячі сплячих потоків × мегабайтні стеки).

Non-blocking режим: ставимо прапор O_NONBLOCK. Тепер read на порожньому сокеті повертає -1 з errno = EAGAIN/EWOULDBLOCK, а не спить. Як дочекатися готовності, не блокуючись по одному дескриптору? poll/epoll.

⬡ poll(): портативне очікування
#include <poll.h> struct pollfd { int fd; short events; // POLLIN, POLLOUT, POLLERR, POLLHUP short revents; // що ядро виставило }; int poll(struct pollfd *fds, nfds_t nfds, int timeout_ms); # повертає кількість fd з ненульовими revents, 0 при таймауті, -1 при помилці
struct pollfd p[3]; p[0].fd = listener; p[0].events = POLLIN; p[1].fd = sock1; p[1].events = POLLIN; p[2].fd = sock2; p[2].events = POLLIN; while (1) { int n = poll(p, 3, -1); if (n < 0) { perror("poll"); break; } for (int i = 0; i < 3; i++) { if (p[i].revents & POLLIN) { // обробити готовий fd } } }

poll працює, але лінійно скануєш усі N дескрипторів на кожен event. Для 100К з'єднань це повільно.

⬡ epoll(): Linux-спосіб масштабувати

Замість того щоб щоразу передавати ядру список fd, epoll тримає в ядрі persistent множину спостережуваних дескрипторів і повертає лише готові.

#include <sys/epoll.h> int epoll_create1(int flags); // EPOLL_CLOEXEC int epoll_ctl(int epfd, int op, int fd, struct epoll_event *ev); int epoll_wait(int epfd, struct epoll_event *out, int maxevents, int timeout_ms); # op: EPOLL_CTL_ADD | EPOLL_CTL_MOD | EPOLL_CTL_DEL struct epoll_event { uint32_t events; // EPOLLIN, EPOLLOUT, EPOLLET, EPOLLONESHOT, ... epoll_data_t data; // user-pointer або fd };
int ep = epoll_create1(EPOLL_CLOEXEC); struct epoll_event ev = { .events = EPOLLIN, .data.fd = listener }; epoll_ctl(ep, EPOLL_CTL_ADD, listener, &ev); struct epoll_event events[64]; while (1) { int n = epoll_wait(ep, events, 64, -1); for (int i = 0; i < n; i++) { int fd = events[i].data.fd; if (fd == listener) { int c = accept4(listener, NULL, NULL, SOCK_NONBLOCK); ev.events = EPOLLIN | EPOLLET; // edge-triggered ev.data.fd = c; epoll_ctl(ep, EPOLL_CTL_ADD, c, &ev); } else if (events[i].events & EPOLLIN) { // дочитувати у циклі, поки read != EAGAIN (для ET — обов'язково) } } }
Level-triggered (LT) vs Edge-triggered (ET). LT (за замовч.): подія повторюється, поки в буфері є дані — простіше, можна читати по шматочку. ET: подія приходить один раз, коли стан змінюється з «нема» на «є» — швидше, але треба читати/писати у циклі до EAGAIN, інакше «застрягне». ET вимагає non-blocking сокетів.

epoll віддає тільки готові дескриптори: складність epoll_wait — O(готових), не O(всіх). Це і є відповідь на C10K-проблему. Аналоги: kqueue у BSD/macOS, IOCP у Windows; крос-платформні бібліотеки — libuv, libevent, boost::asio.

⬡ Сценарії з Lab 5

Сценарій 1 — echo-сервер на тисячі з'єднань. thread-per-connection вмирає на ≈10К (стек × N = ГБ). Розв'язок: один потік + epoll, або thread pool + epoll з розподілом fd по потоках.

Сценарій 2 — produce/consume. Один продюсер, кілька консьюмерів: захищена черга з cv.wait; для високого throughput — lock-free MPMC-черга на CAS.

Сценарій 3 — паралельний обчислювальний пул. Розбий задачу на чанки, кинь у thread pool, збирай результати. Розмір пулу = число ядер; уникай false sharing (вирівнюй per-thread дані по cache line).

Контрольні запитання: Що спільне і що окреме в потоків одного процесу? Чим mutex відрізняється від семафора (хто власник)? Що таке spurious wakeup і як від нього захиститися? Що таке CAS і ABA-проблема? Lock-free vs wait-free? Різниця LT і ET у epoll? Чому ET вимагає O_NONBLOCK? Коли poll кращий за epoll? Чому thread-per-connection не масштабується?
Що варто запам'ятати
  • Потоки одного процесу поділяють heap, globals, fd-таблицю; кожен має свій стек і регістри.
  • Race condition: x++ — це read+inc+write; між інструкціями може втрутитись інший потік. Лікує std::mutex або std::atomic.
  • Mutex дорогий при суперечці (system call). atomic — одна CPU-інструкція. Lock-free = усе на CAS-циклі.
  • Edge-triggered epoll вимагає O_NONBLOCK + читання у циклі до EAGAIN; інакше «застрягне».
  • Thread pool + epoll — стандартний рецепт для серверу на 100K+ з'єднань (відповідь на C10K-проблему).
